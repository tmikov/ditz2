Reported by an agent using dz, and it is the only time the tool pushed a caller
outside its own contract.

`dz set` covers title, component, status and assignee. It does not cover the
body. `dz edit` does, but it wants `$EDITOR`, and under `--json` it refuses on
conflict rather than resolving one. So a non-interactive caller that needs to
revise a description has no supported path.

What actually happened: revising the mandreel issue's description (adding the
"originally filed as component vm" note) left editing the Markdown file
directly as the only option. That bypasses the project lock and writes no log
entry — the two things dz otherwise guarantees about every mutation. A caller
following the tool's own rules cannot do a thing the tool's own storage format
makes trivial, so the rule-following path is the one that corrupts the
invariants.

Suggested shape, from the report: `dz set <id> --body -` reading stdin, and/or
`--append-body -` for the common case of adding a note without restating the
whole description. Either records a log entry like every other `set` field.

Worth noting while designing it:

- `dz add` already has exactly this affordance — `-m, --message <text>` with
  `-` meaning stdin. The asymmetry is that `add` can write a body and `set`
  cannot change one.
- `set` appends a log entry for every field it is *given*, changed or not
  (measured, not inferred). A `--body` that rewrites an identical body would
  add a no-op log line, so the same diffing the TUI form does belongs here.
- `set` has no compare-and-swap; `saveEdited` does. A stdin body arriving
  against a stale read would silently overwrite a concurrent change. Decide
  whether `--body` takes `edit`'s baseline discipline or `set`'s
  last-writer-wins, and say which in the help text — this is the distinction
  `ui/README.md` got wrong and had to be corrected.
- Whatever lands should be reachable from the facade too, so `ditz2-ui` can use
  it for plan 2d's `$EDITOR` body editing rather than growing a second path.
