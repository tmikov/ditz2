findIssue no longer parses every file, but list and grep still must: they genuinely need every issue in order to filter or search. That is the right cost at the scale this tool targets, and it stays right for a long time. Filing so the option is recorded rather than rediscovered.

Sketch: a gitignored dz/cache.sqlite holding parsed issues keyed by filename, with mtime and size for invalidation. Any file whose stamp does not match is reparsed and the row replaced; anything missing is dropped. The cache is built on demand and never required.

Constraints that matter more than the speedup:

- The Markdown files stay authoritative. The cache must be deletable at any moment with no loss, and a cold run must produce identical output to a warm one. That is the property to test: run every command with and without the cache and diff.
- It must be gitignored and never committed. Two people would otherwise merge a binary.
- Spec section 2 rejected a hybrid derived-state design for v1 because it introduces a consistency invariant needing a repair command. A pure cache is weaker than that hybrid, since nothing is only in the cache, but it is the same class of risk and deserves the same suspicion.
- Worth measuring first. Parsing a few hundred small Markdown files is fast, and adding sqlite means a native dependency, a schema, and a migration story for a tool whose selling point is that the database is a directory you can read.
