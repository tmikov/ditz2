dz list --json with a malformed issue file writes "dz: warning: skipping ..." to stderr, not JSON, and exits 1.

stdout stays clean so the primary contract holds, but an agent has no machine-readable way to learn which file was skipped. Spec section 7 promises the envelope on stderr in --json mode.

Emit one envelope per failure, or a single {"warnings":[...]} line.

    Partial failure now writes {"warnings":[{"file","code","message"}]} to stderr under --json, one compact object on one line, with stdout and the exit code unchanged.

    The rule this buys: under --json stderr is empty or exactly one json object, carrying an error key, a warnings key, or both. One parse, no line splitting, no sniffing whether a line is prose.

    Kept the per-file code because the remedies differ: CONFLICT_MARKERS means finish the merge, PARSE_ERROR means the file is malformed. Rejected putting warnings inside the stdout payload, which would have changed dz list --json from an array to an object and broken every existing consumer.

    README and dz help agents both updated.
