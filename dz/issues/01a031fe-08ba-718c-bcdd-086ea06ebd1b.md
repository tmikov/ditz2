Agents are a first-class consumer, but the JSON shape is only described in prose across the README and dz help agents. A versioned schema would let a consumer validate, and would make a future field change visible rather than silently breaking parsers.

Sketch: a schemaVersion in each payload, and a checked-in JSON Schema for the issue object plus the error and warnings envelopes, with a test asserting real output validates against it. That test is the part with actual value; the file alone drifts.

NEEDS A DECISION on whether to add a version field to every payload, which is itself a breaking change to the current shape.

    Added dz schema, printing a JSON Schema for every --json payload: issue, issue list, error envelope, warnings envelope, doctor report, init result, component list.

    Decided against a schemaVersion field in each payload. dz list --json is a bare array, so versioning in-band means wrapping it in an object, which breaks every existing caller and makes list inconsistent with show. That is the same objection that ruled out putting warnings in the stdout payload. The document carries the version instead, in $id and schemaVersion.

    The valuable part is the test: ajv validates real output from every command against the schema, including two cases asserting the schema is strict enough to reject an added field or a missing one. A schema nobody checks drifts within a release.
