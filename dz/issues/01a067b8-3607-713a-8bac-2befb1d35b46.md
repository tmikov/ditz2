Every issue carries type, status, component and assignee, but nothing says how
much it matters. Sorting a backlog of 26 issues by "which of these should I do
next" currently means reading all of them.

Open questions for whoever picks this up:

- Severity and priority are not the same axis. Severity is a property of the
  defect (how bad is it when it happens); priority is a decision about
  scheduling (when will we do it). Tools that conflate them end up with a
  single field nobody trusts. Decide whether this is one field or two before
  designing the storage.
- Whatever it is, it needs a vocabulary, and by this project's own rule that
  vocabulary lives in `src/core/types.ts` and is exported from the facade —
  never retyped by a consumer. `SETTABLE_STATUSES` and `ISSUE_TYPES` are the
  pattern to copy.
- It has surfaces: `dz list` output, `dz show`, the filter grammar, the TUI's
  list columns, and the TUI form's pickers. Plan 2c's form is built from
  `fieldsFor(mode)`, so adding a picker there is cheap; the list columns are
  the expensive part, since the terminal width budget is already tight.
- Existing issues have no value for it. Decide whether that reads as a
  distinct "unset" or defaults to a middle value, and make `dz doctor` say
  which.
